Fix the Artwork

A browser-based jigsaw puzzle that brings artwork reconstruction to the web. An offshoot of Fix the Artefact — rebuilt for the browser with a focus on art appreciation, smooth interaction, and accessible play.

Role Designer & Developer
Type Interactive Web App
Stack HTML5 Canvas, JavaScript, CSS

Overview

Fix the Artwork takes the core idea behind Fix the Artefact — reconstructing images as a puzzle — and moves it to the browser. Instead of archaeological artefacts in a museum kiosk, the focus shifts to artworks: paintings, illustrations, and visual compositions that reward close looking.

The project is a deliberate reinterpretation rather than a port. The interaction model, visual design, and technical architecture were all rethought for the web, taking advantage of what the browser does well while solving the constraints that came with the original Java desktop application.

Why I Made This

Fix the Artefact worked as a dissertation project, but it was locked inside a Java desktop app. I wanted to see what the same concept looked like when it could run anywhere — no install, no setup, just a URL.

Shifting the subject matter from artefacts to artwork also changed the design problem. Artwork demands more visual fidelity, smoother interaction, and a presentation layer that doesn't compete with the image. The puzzle needed to feel like a gallery, not a game UI.

This was also a chance to apply what I'd learned from the first version: what the user testing revealed, what the accessibility review flagged, and what felt clumsy in the original interaction model.

User Experience

Users select an artwork from a curated gallery. The image is divided into jigsaw pieces rendered on an HTML5 Canvas. Pieces can be dragged, rotated, and snapped into place with smooth visual feedback — soft shadows when lifting, a subtle settle animation on placement.

The surrounding UI is deliberately minimal. No score counters, no timers, no leaderboards. The emphasis is on the act of looking closely at an image and understanding its composition through the process of reassembly.

Completing a puzzle reveals the full artwork alongside contextual information: the artist, the period, a short description of the work's significance. The educational layer is present but never forced.

Key Features

  • Canvas-based puzzle engine — pieces are generated dynamically from any source image with configurable grid sizes and organic jigsaw edge shapes.
  • Smooth drag and snap — lift, move, and place pieces with responsive visual feedback. Proximity-based snapping with a satisfying lock animation.
  • Piece rotation — optional rotation adds difficulty without cluttering the interface. Controlled via scroll wheel or tap gesture.
  • Curated artwork gallery — a selection of paintings and illustrations chosen for visual variety and puzzle suitability.
  • Responsive layout — the canvas and UI adapt to any screen size. Playable on desktop and tablet without compromise.
  • Accessibility — keyboard controls for piece selection and placement, high-contrast outlines, and screen reader announcements for progress and completion.
  • Zero dependencies — vanilla JavaScript, no frameworks. Fast load, no build step required.

Technical Architecture

The entire application runs client-side in the browser with zero external dependencies. The puzzle engine handles piece generation, hit detection, snap logic, and rendering in a single requestAnimationFrame loop.

Fix the Artwork ├── engine/ │ ├── puzzle.js — Piece generation, edge shapes, grid layout │ ├── canvas.js — Rendering pipeline, layering, viewport management │ ├── interaction.js — Drag handling, snap detection, rotation input │ └── animation.js — Lift shadows, snap settle, completion transitions ├── gallery/ │ ├── artworks.json — Artwork metadata, descriptions, artist info │ └── images/ — Source artwork files (optimised for web) ├── ui/ │ ├── selector.js — Artwork gallery browser │ ├── controls.js — Difficulty picker, hint toggle, reset │ └── completion.js — End state display, artwork info reveal ├── accessibility/ │ ├── keyboard.js — Arrow-key piece selection and placement │ └── announcer.js — Live region updates for screen readers ├── styles/ │ └── app.css — Minimal UI styling, responsive layout └── index.html — Single entry point

Piece edges use Bezier curves generated from a seed, ensuring consistent interlocking shapes. Hit detection uses path-based point-in-polygon testing on the canvas context. The snap system groups connected pieces so they move as clusters once joined.

Relationship to Fix the Artefact

Fix the Artefact was the starting point — it proved the concept and identified the design problems worth solving. Fix the Artwork is the iteration that addresses them:

  • Platform — Java desktop → browser. No install barrier, works on any device with a modern browser.
  • Interaction quality — Swing drag-and-drop → Canvas with smooth animation. The tactile quality of moving pieces improved significantly.
  • Subject matter — archaeological artefacts → artwork. A broader, more accessible content library.
  • Accessibility — bolt-on accommodations → built-in from the start. Keyboard controls and screen reader support were part of the architecture, not afterthoughts.
  • Deployment — standalone executable → static files. Hostable anywhere, cacheable, instantly shareable via URL.

Reflections

Rebuilding a project from scratch in a different technology taught me more than the original build. Decisions I'd made unconsciously in Java — layout management, event handling, rendering strategy — had to be made deliberately in the browser. That forced clarity.

The biggest lesson was about interaction feel. The Java version worked correctly but felt mechanical. Moving to Canvas with requestAnimationFrame and adding subtle animation details — lift shadows, easing on snaps, a slight bounce on completion — made the same puzzle feel genuinely different to use. Correctness isn't enough; feel matters.

Working without frameworks was a deliberate choice. For a project this focused, the overhead of React or a game engine would have added complexity without solving real problems. Vanilla JavaScript kept the feedback loop tight and the bundle nonexistent.
